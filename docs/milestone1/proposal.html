Proposal at a glance

Computational problem. MetroFlow is a flood-response and rescue-dispatch system. Its core computation is a vehicle-specific, flood-aware shortest-time path on a live road graph: given a rescue vehicle's ground clearance and the current standing-water depth on every road segment, find the fastest route that never enters a segment the vehicle cannot cross.

Primary algorithm. A* search with a min-heap frontier, an admissible and consistent great-circle/top-speed heuristic, a hard clearance cut-off, and a depth-dependent speed-degradation edge cost [1], [2]. This is implemented in backend/routing.py (td_a_star_search).

Supporting algorithms. The backend contains 18 more algorithms beside A*: the hydrology model that generates the depths, passability rules, turn-by-turn steps, a dispatch preview, a nearest-node snap, the CR-004 flood-state resolver, report urgency ranking, a duplicate-neighbour map, a sensor/report mismatch check, evidence checks, a tamper-evident audit hash chain, a rate limiter, event replay, spatial queries, an advisory upsert, JWT sessions and the seed builder. Each is numbered ALG-02 to ALG-19 and gets the same treatment as A* inside every task: its own formal specification (Task 1), strategy table and pseudocode (Task 2), complexity and scalability table with a measured result (Task 3), interface contract (Task 4), story and work-package ticket with a benchmark assertion (Task 5), and answers (Task 6). Task 1: Computational Problem Modeling & Formal Mathematical Formulation

Waterfall phase: Requirements. This task restates the routing requirements (FSD-FR-011 to 017, FSD-FR-089) as a mathematical problem.

1.1 Problem statement & domain context

During typhoon-driven flooding, standing water makes road segments impassable for some vehicles and merely slow for others. A rescue unit with 28 cm of ground clearance cannot use a lane that a 70 cm truck can. Routing that ignores depth and vehicle clearance sends units into submerged streets. The operational question is therefore: for a given vehicle, what is the fastest route to a victim that only uses road segments the vehicle can actually cross, and does any such route exist?

Flood depth is a standard predictor of road-network disruption: speed falls as depth rises and vehicles stop at a depth tied to their clearance [7]. Prior work on emergency services during floods assigns depths to road links and derives reduced vehicle speeds and service areas from them [6]. MetroFlow adopts the same modelling idea, using a per-vehicle clearance threshold and a depth-dependent speed penalty, and runs it on a live, sensor- and report-updated graph. Shortest-path search under constraints is a core graph problem [1], and goal-directed A* search is the standard way to cut the explored region on road networks [2], [5].

1.2 Flood-aware A* (ALG-01, primary): formal specification

Input parameters (\(I\)). A directed graph \(G=(V,E)\) with \(|V|=n\), \(|E|=m\). Each node \(u\in V\) has a coordinate \(x_u=(\varphi_u,\lambda_u)\) (latitude, longitude). Each edge \(e=(u,v)\in E\) has length \(\ell_e>0\) (m), posted speed \(s_e>0\) (km/h) and live water depth \(d_e\ge 0\) (cm). A query supplies a source \(s\in V\), target \(t\in V\) and vehicle clearance \(c>0\) (cm).

Depths \(d_e\) are produced by the hydrology engine: for rainfall \(P\) (mm), curve number \(CN\), \(S=\tfrac{25400}{CN}-254\) and initial abstraction \(I_a=0.2S\), the direct runoff is \[ Q=\begin{cases}0 & P\le I_a\\[2pt] \dfrac{(P-I_a)^2}{P-I_a+S} & P>I_a\end{cases}\] which is then scaled to a street ponding depth in cm [8]. Verified hazards and sensor breaches can additionally close edges.

Boundary conditions & constraints (\(C\)).

  • Passability: \(d_e < c\) (an edge with \(d_e \ge c\) is submerged and removed). The feasible subgraph is \(G_c=(V,E_c)\), \(E_c=\{e: d_e
  • \(0 < c \le 200\) cm (enforced at the API); \(s,t\in V\).
  • Effective speed floor: \(v_e \ge 0.5\) m/s so every traversal time is finite.
  • Depth and speed are in cm and km/h throughout (project unit policy).

Objective function (\(f\)). This is an optimization problem (minimization) over \(s\)–\(t\) paths in \(G_c\). Define the depth-degraded speed and traversal time of an edge: \[ v_e=\max\!\Big(\frac{s_e/3.6}{1+(d_e/10)^{1.8}},\;0.5\Big)\ \text{[m/s]},\qquad w_e=\frac{\ell_e}{v_e}\ \text{[s]} \] \[ \min_{P=(e_1,\dots,e_k)\ \text{path } s\to t\ \text{in } G_c}\ T(P)=\sum_{i=1}^{k} w_{e_i} \] A companion decision problem is: does an \(s\)–\(t\) path exist in \(G_c\)? This is the 404 / "no safe route" case.

Output certificate (\(O\)). A deterministic tuple \((\text{status},\,P^*,\,T^*)\): status ∈ {OK, NO_SAFE_ROUTE, INVALID_NODE}; \(P^*\) the node sequence; \(T^*=T(P^*)\) the minimal travel time. If no path exists, \(P^*=\emptyset\) and \(T^*=\infty\). Optimality is checkable: \(T^*\) must equal the Dijkstra reference value on the same \(G_c\) [4].

Dispatch extension. For an SOS with \(K\) candidate vehicles, each with clearance \(c_k\) and position \(s_k\), the preview solves \(K\) independent instances and ranks units by \(T^*_k\).

Task 2: Algorithmic Paradigm Selection & Logic Specification

Waterfall phase: Design (TSD §2 Algorithms, ADR-004). The choice below is already recorded as an accepted design decision. The template asks for one core algorithm, so A* is ALG-01; the other 18 algorithms in the system follow in 2.2 with the same schema.

Schema FieldTeam Engineering Details
Algorithm NameClearance-Constrained, Depth-Penalized A* (implemented as td_a_star_search; "time-dependent" in the sense that edge costs are recomputed from the live depth state on every query, not that cost varies during one search).
Design ParadigmGraph Algorithms & Network Theory: best-first search with an admissible, consistent heuristic over a min-heap priority queue.
Foundational ReferencesHart, Nilsson & Raphael (A*) [2]; Dechter & Pearl (optimality of A*) [3]; Dijkstra [4]; Cormen et al., Ch. 22 and 24 [1]; road-network context in Bast et al. [5].
Baseline AlternativeExhaustive simple-path enumeration (DFS with no pruning), then take the minimum. Secondary baseline: Dijkstra (\(h\equiv 0\)), which is correct but explores in all directions.
Computational JustificationThe number of simple \(s\)–\(t\) paths grows factorially in \(n\), so enumeration is infeasible beyond toy graphs. A* returns the same optimum in \(O(m\log n)\) and, with a consistent heuristic, settles each node at most once; the heuristic additionally steers the frontier toward \(t\), expanding fewer nodes than Dijkstra [1], [2], [3]. Measured (Section 3.5): 33–43% fewer nodes settled and identical cost on 120 of 120 queries, but about 18–52% more wall time in pure Python because the haversine heuristic is costly.
Invariants & Recurrence Relations Bellman recurrence on the feasible graph: \(g(s)=0,\quad g(v)=\min_{(u,v)\in E_c}\big(g(u)+w_{uv}\big)\). Priority: \(f(v)=g(v)+h(v)\).
Heuristic: \(h(v)=\dfrac{\mathrm{hav}(x_v,x_t)}{v_{\max}}\), \(v_{\max}=\max_e s_e/3.6\).
Admissible: \(w_{uv}\ge \ell_{uv}/v_{\max}\ge \mathrm{hav}(x_u,x_v)/v_{\max}\) (the penalty factor is \(\ge1\)), so \(h\) never overestimates the remaining time.
Consistent: \(h(u)\le w_{uv}+h(v)\) by the triangle inequality of great-circle distance, so \(f\) is non-decreasing along any path and the first time a node is popped its \(g\) is optimal [2], [3].
Loop invariant: every node in settled has final optimal \(g\); every heap entry has \(g\ge g_{\text{best}}\).

2.1 Flood-aware A* (ALG-01, primary): structured pseudocode

TD-ASTAR(G, coords, s, t, c):                  // G: adjacency u -> [(v, len_m, speed_kmh, depth_cm)]
 1  if s not in coords or t not in coords: return (INVALID_NODE, [], inf)
 2  if s == t: return (OK, [s], 0)
 3  v_max  ← max(max over all edges of speed_kmh / 3.6, 0.1)           // m/s, fixed for this query
 4  h(x)   ← haversine(coords[x], coords[t]) / v_max
 5  g[x]   ← inf for all x;  g[s] ← 0;  parent ← {};  settled ← {}
 6  PQ     ← min-heap { (h(s), 0, s) }                                   // (f, g, node)
 7  while PQ not empty:
 8      (f, gu, u) ← POP-MIN(PQ)
 9      if u in settled or gu > g[u]: continue                            // stale duplicate
10      settled ← settled ∪ {u}
11      if u == t: return (OK, RECONSTRUCT(parent, s, t), g[t])
12      for (v, len, speed, depth) in G[u]:
13          if depth ≥ c: continue                                          // hard clearance cut-off
14          pen ← 1 + (depth / 10)^1.8                                    // depth penalty, pen ≥ 1
15          v_eff ← max((speed / 3.6) / pen, 0.5)                         // m/s, floor keeps cost finite
16          g' ← gu + len / v_eff
17          if g' < g[v]: g[v] ← g'; parent[v] ← u; PUSH(PQ, (g' + h(v), g', v))
18  return (NO_SAFE_ROUTE, [], inf)                                            // frontier exhausted: t unreachable in G_c

RECONSTRUCT(parent, s, t): follow parent[] from t back to s; reverse.

Termination: each node is settled at most once and edges are finite, so the loop ends in at most \(m+1\) pops; line 18 is the termination certificate for the infeasible case.

Task 3: Theoretical Asymptotic Analysis & Scalability Profiling

Waterfall phase: Design. The analysis is done before verification, so that the benchmarks in 3.5 and 3.6 have a prediction to be checked against.

3.1 Worst-case time \(O(\cdot)\)

  1. Initialisation (lines 3–6): scanning all edges for \(v_{\max}\) is \(O(m)\); setting \(g[x]=\infty\) for all nodes is \(O(n)\). Subtotal \(O(n+m)\).
  2. Settlement bound. Because \(h\) is consistent (Task 2), a node's first valid pop carries its optimal \(g\) and it is never re-expanded [3]. Hence lines 10–17 run for each node at most once.
  3. Relaxations. Line 12 iterates the out-edges of the settled node, so across the whole run each edge is examined at most once: at most \(m\) executions of lines 13–17, each \(O(1)\) apart from the push.
  4. Heap operations. Each successful relaxation pushes one entry, so at most \(m+1\) entries are ever pushed and popped. Each push or pop costs \(O(\log |PQ|)\le O(\log (m+1))\). Since \(m\le n^2\), \(\log m\le 2\log n\), i.e. \(O(\log n)\) [1].
  5. Total. \(T_{\text{worst}}(n,m)=O(n+m)+O\big((m+1)\log n\big)=O(m\log n)\) for a connected road graph (\(m\ge n-1\)). With \(h\equiv0\) the same bound is Dijkstra's with a binary heap [1], [4]; A* never does worse.

The master theorem does not apply: the algorithm is iterative, with no divide-and-conquer recurrence [1].

Baseline: exhaustive simple-path enumeration visits up to \((n-2)!\) paths on a dense graph, i.e. \(O(n!)\) [1].

3.2 Best- and average-case time \(\Omega(\cdot)\), \(E[\cdot]\)

Best case. If \(h\) is near-perfect (a near-straight, uniform-speed corridor), the search only settles nodes on the path of length \(k\): \(\Omega(k\log n)\) plus the \(O(n+m)\) initialisation done by the current code.

Average case. City road graphs are sparse (\(m=\Theta(n)\), degree about 3–4) and near-planar. A goal-directed search settles only a region around the straight line \(s\to t\), fewer than \(n\) nodes. Measured on a synthetic grid (Section 3.5): 33–43% fewer nodes than Dijkstra, and median runtime growing 3.5× and 4.3× for each 4× increase in nodes. This is a modest saving, not the corridor-only behaviour sometimes quoted for A* [5], because random speeds and flooding weaken the heuristic. We do not claim a closed-form bound. Heavy flooding lowers \(v_e\) while \(v_{\max}\) is unchanged, which weakens \(h\) and moves the average case toward Dijkstra's.

3.3 Auxiliary space \(S(\cdot)\)

g, parent, settled: \(O(n)\) each. Heap: lazy deletion allows stale duplicates, so up to \(m+1\) entries. No recursion (iterative loop, path rebuilt iteratively). Total \(S=O(n+m)\). The graph itself is \(O(n+m)\) input, not auxiliary.

4.1 Component diagram

Current state vs. target. Today routing.py is already a pure module: it imports no ORM, HTTP or database code and takes plain dicts and numbers. FastAPI endpoints (main.py) load the graph with SQLAlchemy, call it in-process, and format the response. The target shown by the dashed boxes moves the call behind a job queue and a worker, so the engine can be scaled and timed out independently of web threads. Boundaries: Presentation never reaches the database; the gateway owns auth, validation and persistence; the engine owns computation only [12].

4.2 Interface data contract

Request: POST /api/v1/algorithm/solve (JSON, application/json, JWT bearer; documented as OpenAPI 3.1 [11]). It generalises the existing GET /api/v1/routing/navigate and GET /api/v1/dispatch/{id}/preview.

Task 6: Academic Review Questions & Defense Checkpoints

Q1. Why must heavy algorithmic processing be decoupled from database ORMs and web request threads?

(a) Responsiveness: a CPU-bound search holds a worker thread for its whole run; with a bounded thread pool, \(K\) concurrent searches starve unrelated requests (login, map reads) [12]. Moving them to a worker pool behind a queue [15] bounds request latency and allows independent scaling. (b) Testability and correctness: a pure function over plain numbers can be unit-tested and fuzzed against a reference (Dijkstra) without a database; ORM lazy loading inside the loop would add a hidden query per edge, turning \(O(m\log n)\) compute into \(O(m)\) database round-trips. (c) Consistency: the engine should read an immutable snapshot so concurrent depth writes cannot change costs mid-search, which would break the optimality argument. (d) Replaceability: the same engine can be called by the dispatch preview, the driver app and batch jobs. In a waterfall plan this also keeps the design stable: the contract in Task 4 is fixed at the Design gate, so the engine can be re-implemented without reopening the API.

Q2. If the algorithm has exponential worst-case complexity, what keeps it viable?

Our core engine is not exponential: it is \(O(m\log n)\) (Task 3). The exponential algorithm is the baseline (path enumeration). Had we extended the problem to a multi-criteria or capacity-constrained variant, which is NP-hard, we would use pruning by the admissible bound \(f\) [2], [3], dominance pruning, and an \(\varepsilon\)-bounded weighted A* (\(f=g+(1+\varepsilon)h\)) that guarantees a cost within \((1+\varepsilon)\) of optimal, plus the per-request time_limit_ms returning the best route found with truncated=true.

Q3. Exact vs. approximate / heuristic algorithms in production?

An exact algorithm guarantees the optimal answer and a checkable certificate, at a cost that may grow quickly. A heuristic or approximate algorithm trades a bounded or unbounded loss in quality for speed [1]. Our A* is exact because \(h\) is admissible and consistent [2], [3]; "heuristic" describes how it is guided, not that its answer is approximate. In a rescue setting a wrong (non-optimal) route has a safety cost, so we keep the exact search and use an approximate variant only as a time-limited fallback. The hydrology model, by contrast, is an approximation (SCS-CN, a decision aid, not a hydrodynamic model) [8], and we label it as such.

Q4. Empirical benchmarking vs. asymptotic analysis?

Asymptotic analysis is done before implementation, in the Design phase, on a model of computation, and states how cost grows with \(n,m\) while ignoring constants, hardware and the interpreter [1]. Empirical profiling is done after implementation, in the Verification phase, on real code and data, and measures constants, cache and Python overhead, and the average case that theory cannot give in closed form. We use both: Task 3 predicts \(O(m\log n)\); the benchmark harness (Tasks 3 and 5) checks the growth trend (runtime vs. \(N\)) and enforces an absolute budget (p95 < 50 ms at N = 5,041). Neither replaces the other: a good bound with a slow constant can still miss a latency budget (our A* settles fewer nodes than Dijkstra yet runs slower in Python), and a fast run on one dataset proves nothing about the worst case.

Q5. Cold start / data sparsity (if ML or preference matrices are used)?

The routing engine uses no learned model or user-preference matrix, so the classic cold-start problem does not apply. The analogous risk is sparse live data: few sensors and reports at launch, so many edges have no measured depth. Mitigation: default unknown edges to the hydrology engine's modelled depth [8], treat sensor and verified-report values as overrides, and surface edges without recent data as lower-confidence rather than silently safe. If we later add a learned depth predictor, we would seed it from the physical model and historic flood records.

Q6. How are edge-case inputs handled without crashing the service?

Every degenerate input has a defined return value rather than an exception: unknown nodes → INVALID_NODE; s = t → zero-length path; disconnected subgraphs or fully flooded corridors → the frontier empties and the search returns NO_SAFE_ROUTE (the termination certificate in line 18); cycles are harmless because settled makes every node expand once [1]; the speed floor removes division by zero. No singular-matrix case arises, as the engine uses no linear algebra. Inputs are validated at the gateway (Pydantic, bounded ranges) and errors are returned as RFC 9457 problem documents [9], so a bad request cannot take down the worker.

Pseudocode (core loop)

g[s]=0; PQ={(h(s),0,s)}; settled={}
while PQ not empty:
    (f, gu, u) = pop_min(PQ)
    if u in settled or gu > g[u]: continue
    settled.add(u)
    if u == t: return path, g[t]
    for (v, len, speed, depth) in G[u]:
        if depth >= c: continue                  # clearance cut-off
        pen   = 1 + (depth/10)^1.8
        v_eff = max((speed/3.6)/pen, 0.5)
        g2    = gu + len / v_eff
        if g2 < g[v]: g[v]=g2; parent[v]=u; push(PQ,(g2+h(v), g2, v))
return NO_SAFE_ROUTE

Defense highlights

  • Why decouple? CPU-bound search starves request threads; pure function is fuzz-testable; immutable snapshot keeps optimality valid.
  • Exact vs heuristic: our A* is exact (admissible + consistent); weighted A* only as a time-limited fallback.
  • Theory vs benchmark: Big-O at Design predicts growth; CI at Verification measures constants and the average case.
  • Sparse data, not cold start: default to modelled depth [8]; mark stale edges low-confidence.
  • Edge cases: defined statuses, never exceptions; cycles harmless via settled.
