## 1. Summary

CR-001 extends the pilot from an LGU-only simulation and triage tool into the
full use-centred design (UCD) scope:

1. a native Expo driver and commuter app (iOS and Android) that provides
   flood-aware navigation, turn-by-turn guidance, proximity warnings,
   evidence-based hazard reporting, offline operation, telemetry and one-tap
   emergency rescue requests;
2. a live LGU operational map with a working moderation queue, evidence
   verification, map drawing tools, fleet monitoring, distress incidents and
   flood-safe dispatch;
3. shared authentication, role-based access control and an event stream that
   publishes a verified hazard to connected clients as soon as a dispatcher
   approves it;
4. river and rain gauge ingestion that flags impacted road segments.

The change supersedes the v1.0 exclusions for a driver client, live sensor
ingestion and real report intake. It adds a native Expo driver app and EAS
internal distribution builds. It does **not** add a public App Store or Play
Store release, a real CCTV integration, production SMS or telephony, multi-LGU
tenancy or a public information portal.

## 2. Reason

The v1.0 pilot demonstrates simulation, routing and a triage screen, but the
operational loop is incomplete:

- the portal queue is mock data, so a decision does not change anything;
- there is no map, so a dispatcher cannot see a hazard or a unit in space;
- there is no driver client, so verified information never reaches the people
  who need it;
- there is no sensor input, so the road picture depends entirely on manual
  observation;
- there is no authentication, so no privileged action can be trusted.

Without these elements the system cannot show the intended benefit: a verified
field observation becomes a published hazard, a driver is rerouted around it, and
a rescue unit is dispatched on a route that avoids it.

## 4. Impact Analysis

### 4.1 Requirements and traceability

All new requirements trace from `BR-013`–`BR-018` through `FR-013`–`FR-018` and
`FSD-FR-054`–`FSD-FR-093` to test scenarios and technical test cases. Existing
identifiers are unchanged; the change adds rows and never renumbers.

The v1.0 boundary statement in the BRD, charter, FSD and PMP is replaced. The
out-of-scope lists in those documents now match §3.2.

### 4.2 Architecture

| Component        | Change                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------ |
| Driver client    | New `metroflow-mobile/` native Expo app: Expo SDK 58, React Native 0.88, React 19, TypeScript, Expo Router, React Navigation, `react-native-maps`, `expo-location` |
| LGU portal       | Existing Next.js shell gains a MapLibre map, live queue, evidence desk, drawing tools, fleet and dispatch          |
| UI source        | Client-supplied HTML/CSS template derived from Figma, adapted into React Native components; no bespoke UI design   |
| Styling          | React Native `StyleSheet` with shared driver tokens; Tailwind CSS 4 remains the admin portal styling                |
| Identity         | The API issues and verifies HS256 session tokens; bcrypt hashes live on the `users` row and roles are checked server-side |
| Mapping          | `react-native-maps` in the driver app and MapLibre on the portal (planned); Mapbox raster tiles via public token, OSM fallback |
| API              | New auth, report, hazard, vehicle, SOS, dispatch and sensor endpoints                                              |
| Event transport  | Server-sent events backed by Redis pub/sub for hazards, fleet and SOS                                              |
| Background work  | Sensor threshold evaluation and telemetry throttling                                                               |
| Evidence storage | Local disk volume for the pilot, behind a storage interface                                                        |

The API remains stateless except for the upload volume and Redis; instances can
still be added horizontally.

### 4.3 Data

New tables: `incident_reports`, `hazard_zones`, `vehicles`,
`vehicle_telemetry`, `driver_locations`, `sos_requests`, `dispatch_tasks`,
`sensors` and `sensor_readings`. `users` gains pilot accounts provisioned through
the Supabase Admin API and `audit_logs` gains a write path. Every table receives
row-level security and `anon`/`authenticated` revocation on the hosted database.

### 4.4 API

New groups: `/auth`, `/reports`, `/hazards`, `/vehicles`, `/sos`, `/dispatch`,
`/sensors`, plus a hazard/fleet event stream and coordinate-based routing with
turn instructions and hazard avoidance. Every route except the auth entry points
requires a bearer token, and writes require a portal role (§8). Contracts are
listed in [api.md](api.md) §9 and specified in [TSD.md](TSD.md).

### 4.5 Security and privacy

- Session tokens signed by the API (PyJWT, HS256) and verified on privileged routes;
  roles enforced by the API and Postgres.
- The portal keeps the token in `sessionStorage` for the browser session and the app
  keeps it in memory; both send `Authorization: Bearer <token>` on every request.
- The service-role key stays server-side and never ships to a client; the public anon
  key is not used by the API.
- `METROFLOW_CORS_ORIGINS` replaces the wildcard with a portal allowlist; credentials
  are only advertised for an explicit list. Public keys are restricted by origin and scope.
- Upload validation: MIME sniff, size limit, re-encode and EXIF stripping.
- Rate limits on login, report submission, telemetry and SOS.
- Driver positions rounded to 50 m, device identifiers salted-hashed, and
  retained for at most 24 hours.
- No privileged action without an immutable audit record.

is generated at deployment for the sensor gateway; it is not a third-party key.
No value in this table is committed to the repository.

## 6. Conditions

1. The driver client is delivered as a native Expo app. Pilot distribution uses
   EAS internal builds/TestFlight; a public App Store or Play Store release is a
   separate gate.
2. Background location and notifications require explicit permission,
   store-compliant disclosures and a foreground fallback. The app must remain
   usable when permission is denied.
3. CCTV remains a labelled demo registry; rain gauges may be simulated but must
   be marked as simulated in the interface and the data.
4. The sub-100 ms publication target is measured from server publish to emitted
   SSE event; network delivery to a device is reported separately.
5. Offline mode renders the cached road graph; basemap tiles are not claimed
   offline.
6. Every privileged action is role-checked and audited before the increment is
   accepted.
7. No real personal data is used until the privacy controls in §4.5 are verified.
8. The pilot remains single-LGU.
9. The portal and driver app are implemented from the client-supplied HTML/CSS template;
   the document set does not authorise a bespoke visual design.
10. Every credential is supplied by environment or repository secret. Public keys
    are restricted by origin and scope, and the service-role key never reaches a
    client.
