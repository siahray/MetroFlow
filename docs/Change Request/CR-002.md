# **1. Executive Summary**

The current admin documentation and UI baseline assign **Dispatch Radar** to *report verification* (FSD-FR-024–046, `docs/design/ADMIN_UI_BASELINE.md`) while distress/SOS assignment and dispatch are specified separately under BR-016 / FSD-FR-087–089. This CR proposes a clearer operational split for the admin web:

1. **Triage and Verification → Operations Dashboard:** repurpose the screen as an operations overview/dashboard (not incident verification actions).
2. **Moderation and Evidence → User-generated reports only:** move field verification of user reports into Moderation and Evidence, with strict ownership of report review/evidence/moderation.
3. **Dispatch Radar → User SOS requests only:** restrict Dispatch Radar to SOS/distress incidents and enable **assignment of a specific rescue responder** and **responder tracking during rescue and dispatch**.

Responder tracking is specified to support **both** live GPS/telemetry streaming **and** periodic status/ETA/mission updates. The planned responder client is a **separate responder app or responder mode integrated into the driver mobile app** (either must satisfy the same tracking/dispatch contract defined by this CR). For locality, **Quezon City Hall (Quezon City)** is the defined **LGU operations base**, and **rescue units/fleets are staged in the same vicinity** by default.

# **2. Detailed Scope of Changes**

## **2.1 Admin information architecture and screen ownership**

| Screen | New purpose (strict) | Ownership / notes |
| :---- | :---- | :---- |
| **Triage and Verification** | **Operations dashboard** | Overview/KPIs/operational status and drill-down context as specified. No field-report verification and no SOS dispatch actions. Exact widgets, metrics, data sources, refresh behavior, permissions, and drill-down targets are **[TBC]**. |
| **Moderation and Evidence** | **User-generated reports only** | Owns field verification/review of citizen/driver-submitted reports and associated evidence. Report queue/detail/evidence and moderation actions currently associated with report verification (e.g. FSD-FR-024–046 and related dispatch/verification actions, as applicable) and moderation (FSD-FR-077–081) must be reconciled and re-homed here with unambiguous state/action boundaries. |
| **Dispatch Radar** | **User SOS requests only** | Owns SOS/distress incident visibility, selection, **specific rescue responder assignment**, dispatch/confirmation flow, and **responder tracking during rescue and dispatch**. Must not handle user-generated report verification. |

## **2.2 SOS dispatch and responder assignment (Dispatch Radar)**

* Dispatch Radar lists and manages **SOS/user distress requests only** (app SOS and/or dispatcher-entered distress incidents, as defined in FSD-FR-087 / current distress flow — **[TBC: confirm exact SOS sources in scope]**).
* Admin/dispatcher can **assign a specific rescue responder/unit** to an SOS incident and proceed through the dispatch/confirmation workflow.
* Assignment/dispatch behavior must align with and extend current distress-dispatch requirements/rules where applicable (BR-016, FSD-FR-087–089, BRULE-011) or supersede them explicitly if changed (**[TBC: final FR/BRULE mapping]**).
* Actions, state transitions, permissions (FSD-FR-092), confirmation/undo behavior (where applicable), and audit records (FSD-FR-043/044/047/093) must be specified for the SOS-only flow.

## **2.3 Responder tracking during rescue and dispatch**

Dispatch Radar must present responder tracking using **both** mechanisms:

1. **Live GPS/telemetry stream** — near-real-time responder/unit location and movement updates from the responder client/device.
2. **Periodic status/ETA/mission updates** — discrete mission/status/ETA/progress updates (including poll/refresh-based updates where applicable).

**Specification required [TBC/TBD in implementation spec]:**
* Responder identity/linking (user, unit/vehicle, device/app/session) and how “specific rescue responder” is represented.
* Tracking data contract: fields, coordinate/time source, update cadence/frequency, transport (stream/SSE/WebSocket/polling as chosen), and storage/retention.
* Source of truth and conflict/staleness handling (e.g. live stream vs periodic update, stale fix/offline responder, last-known location).
* Failure behavior and operator-visible states (unavailable, stale, reconnecting, offline).
* Privacy, access control, and audit implications for location/telemetry data.

**Planned responder client (source of tracking/mission data):** a **separate responder app** or **responder mode integrated into the driver mobile app**. CR-002 requires the system contract/interfaces to support either client form.

## **2.4 Moderation and Evidence (user-generated reports)**

* Moderation and Evidence becomes the **only** admin screen/workflow for **user-generated field reports** (verification, evidence review, and moderation actions).
* Field-verification responsibilities currently tied to report verification/triage/Dispatch Radar contexts must be **moved and remapped** here (including reconciliation of FSD-FR-024–046 responsibilities with existing moderation/evidence requirements FSD-FR-077–081).
* Report moderation actions, evidence presentation, auditability, and permissions must remain explicit and role-constrained (**[TBC: final action/state matrix]**).

## **2.5 Locality and operations base**

* **LGU operations base/location:** **Quezon City Hall, Quezon City**.
* **Rescue units and fleet:** staged in the **same vicinity** as Quezon City Hall by default (home/staging base for dispatch context), with **live reported unit position/telemetry taking precedence during active response/tracking** where available.
* **Canonical reference [TBC]:** official address and geographic coordinates (lat/lon) for Quezon City Hall used by the system, and whether “same vicinity” is modeled as a fixed staging point, facility area, or radius.
