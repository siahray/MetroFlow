# **1\. Executive Summary**

Following the baseline transition to the production \~6,177-node OpenStreetMap dataset, live system testing revealed three operational bottlenecks requiring immediate software-level recalibration prior to final panel demonstration:

1. **Hydrological & Simulation Uniformity (Backend Engine)**: Flat node elevations (`10.0m`) caused the flood simulation to render all road segments in a single uniform color regardless of rainfall volume, preventing `TD-A*` flood-avoidance routing from finding impassable hazards.  
2. **Driver Navigation & Search Limitations (Mobile App)**: The driver client previously rendered bare graph lines on a basic raster map and restricted destination searches to exact graph-node names, causing standard searches to return no results when looking for physical places.  
3. **Coordinate-Only Triage Detail (Admin Portal)**: Incident reports and SOS distress signals in the LGU admin panel only displayed raw numerical latitude/longitude coordinates, forcing dispatchers to open external windows to identify physical incident locations.  
4. **Saved Destination Rigidity (Driver Mobile App)**: Quick Picks could only be anchored to a named road node, so saving a physical place or a dropped pin was impossible and reopening a saved shortcut lost the driver's own label and exact point.

**CR-001** unifies all technical remediations into a single baseline change request to establish full operational readiness across the entire application stack.

# **2\. Detailed Scope of Changes**

# **2.1 Sub-System A: Production Network Hydrological Recalibration & Backend API**

* **Deterministic Node Elevation Spread**: Applied `_synthetic_elevation_m` via `backend/update_node_elevation.py` to assign node elevations across a `1.1m – 19.0m` range (1,568 distinct values) without truncating active database tables.  
* **Hydrology Model Recalibration**: Adjusted `depression_factor` (`0.15` \-\> `0.3`) and `ponding_amplification` (`3.5` \-\> `2.4`) to produce a realistic three-way passability split (**PASSABLE**, **LIGHT\_FLOOD**, **SUBMERGED**) at representative storm rainfall rates.  
* **`/simulate` Serialization Optimization**: Updated endpoint serialization to `model_construct` and direct `model_dump_json()`, bypassing FastAPI `jsonable_encoder` overhead on \~13k-feature payloads (aligning with `LIM-028`).  
* **Dynamic Rain-Gauge Re-Centering**: Updated `coverage_for_extent` to dynamically center Open-Meteo rain-gauge telemetry on the active network's geographic extent.  
* **Door-to-Door Route Parameters**: `/routing/navigate` now accepts raw GPS origin and destination coordinates (`origin_lat`/`origin_lon`/`dest_lat`/`dest_lon`/`dest_name`) for dry `FASTEST` Mapbox handoffs.

# **2.2 Sub-System B: Driver Mobile App (Mapbox, Search & Navigation)**

* **Map Engine Swap**: Migrated from `react-native-maps` to `@rnmapbox/maps` for full street basemap rendering; Storm mode dynamically switches to Mapbox's `navigation-night` style.  
* **POI Place Search**: Implemented Mapbox Geocoding as primary search with keyless Nominatim as fallback, reserving graph-node matching as a last resort.  
* **Drop-a-Pin & Label Upgrading**: Enabled long-press pin dropping with immediate graph-node snapping and asynchronous reverse-geocoding label upgrades (guarded by generation counters).  
* **Snap-to-Road Puck & GPS Split**: Position marker snaps to the active route line (`snapToRoute`), while raw GPS fix data continues driving progress, telemetry, and hazard proximity alerts.
* **Quick Picks Place & Pin Saving**: The Quick Picks editor searches places (Mapbox Geocoding with Nominatim fallback, road nodes last) and lets the driver drop a pin on an inline map, so a shortcut can be saved at the place itself, not only a road-graph junction.  
* **Quick Picks Label & Point Preservation**: Saving and reopening a Quick Pick keeps the driver's own label and exact coordinates for door-to-door dry routing, while the nearest road node remains recorded for graph-based planning.

# **2.3 Sub-System C: LGU Admin Dispatch Portal Triage Panel**

* **Incident Location Map**: Added lightweight single-marker MapLibre visualizer (`incident-location-map.tsx`) in the `dispatch-radar.tsx` detail panel using the Carto Positron basemap.  
* **Reverse Geocoded Address Resolution**: Integrated Nominatim reverse-geocoding (`nearby-place.ts`) to display "Near: , " alongside incident coordinates.

# **5\. Amendment A1 — opt-in least-submerged route (21 November 2026)**

This amendment extends CR-001 without changing the 15 November approval or the scope recorded in §§1–4. It is **implemented in the working tree and fully approved** (Project Lead 21 November 2026; QA/Documentation Lead, Academic Adviser and Academic Panel sign-offs recorded 23 November 2026); the original approval block above is untouched.

**Problem:** `/routing/navigate` hard-skipped every edge where `water_depth_cm >= clearance_cm`. The driver app's "Show Unsafe Route" control only set `ignore_hazards=true`, so when a storm put every edge at or above the clearance the response was still 404 — the driver was refused a route even after asking to proceed.

**Scope added:**

* `/routing/navigate` accepts `allow_submerged=true`. The flood-safe search always runs first; the relaxed search runs only when it finds no path, so a safe route is never replaced by a wet one.
* The fallback ranks paths lexicographically: (1) fewest submerged metres, (2) lowest peak depth among submerged segments, (3) shortest travel time (`BRULE-020`). It uses Dijkstra rather than A* because the primary cost is distance, not time.
* The route is returned as a normal `200` with per-segment `status: "SUBMERGED"`; the response schema is unchanged, and clients must warn before the driver starts. `404` remains for unknown nodes and for graphs with no path at all.
* The driver app's existing **Show Unsafe Route** control now sends `allow_submerged=true`, keeps the flag on reroute/refresh/alternative requests, and shows a "Least-submerged route" chip plus an explicit "you may end up submerged" warning. The offline planner mirrors the fallback so losing the connection does not regress to a refusal.
* The LGU admin map and SOS dispatch preview are deliberately unchanged: they keep the hard clearance gate and still refuse unsafe routes.

# **6\. Amendment A2 — driver weather card, report contract tightening, and proximity threshold tuning (21 November 2026)**

This amendment extends CR-001 without changing the 15 November approval or Amendments recorded above. It is **implemented in the working tree and fully approved** (Project Lead 21 November 2026; QA/Documentation Lead, Academic Adviser and Academic Panel sign-offs recorded 23 November 2026); prior approval blocks are untouched.

**Scope added:**

* **Current weather conditions (display-only).** `GET /api/v1/weather/current-conditions` returns `CurrentWeatherResponse` (temperature, humidity, precipitation chance, wind, WMO description, `as_of`) for the driver's own location. It uses the same Open-Meteo source and cache/failure-degradation pattern as the existing rain gate/forecast endpoints, but is **never** a routing or hazard-advisory input. The driver home screen shows the current-conditions card from this endpoint (`metroflow-mobile/src/app/(tabs)/home.tsx`, `api.ts`).
* **Report submission contract tightened.** Field report submission now requires photo evidence (`photo` is required in `POST /api/v1/reports`; missing photo returns 422) and no longer accepts or stores `barangay`. The Alembic migration `e37c7bc39cdb_drop_barangay_from_incident_reports.py` drops `incident_reports.barangay`. The mobile report screen removes the barangay field, requires a photo before submit, and resolves the GPS fix to a human place name for display.
* **Proximity/rain threshold tuning.** `warning_radius_m` is reduced from 200 m to 100 m (configurable, ~100 m short heads-up at the corridor 50 km/h limit). `RAIN_THRESHOLD_MM_HR` is lowered from 0.5 to 0.1 mm/hr so live drizzle raises a rain advisory instead of being treated as silence.
