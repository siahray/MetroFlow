## 1. Summary

CR-003 adds **Sentinel-1 satellite flood observations** as a hazard source for
the final product. Sentinel-1 is a synthetic-aperture radar (SAR) mission, so it
can observe the ground through cloud and at night. The system will ingest
Sentinel-1 products, derive or receive flood-extent polygons, attach acquisition
time and confidence, and present them to an LGU reviewer.

A satellite observation is an **advisory observation**, not an automatically
verified hazard. It becomes a routing input only after the approved verification
policy is met. This preserves the existing rule that unverified observations do
not reroute drivers.

## 2. Reason

Citizen reports and river/rain gauges provide local evidence, but they are
sparse. Sentinel-1 adds wide-area, all-weather observations that can reveal
flooded zones outside the current report and gauge footprint.

The capability must be added carefully:

- Sentinel-1 provides flood **extent**, not reliable water depth.
- Revisit is typically hours to days, not continuous.
- SAR is affected by wind, vegetation, urban geometry, radar shadow and layover.
- A flood polygon over a road does not prove that the road is passable for a
  particular vehicle.

The design therefore separates **observation**, **verification** and **routing**.

## 3. Change Description

### 3.1 In scope

- Authenticate to the approved Copernicus access service with a backend-only
  credential.
- Discover and ingest Sentinel-1 products for the approved coverage area.
- Derive or receive flood-extent polygons with a documented algorithm and
  quality/confidence flags.
- Store the source product ID, acquisition time, processing time, coverage,
  confidence and review status.
- Correlate the flood extent with the road graph, active sensors and citizen
  reports.
- Present pending observations to an authorised dispatcher for review.
- Publish a verified hazard or dismiss the observation with a reason.
- Stream verified hazards to the admin and mobile clients.
- Include the latest **verified** satellite flood snapshot in an Offline Area,
  with acquisition time and expiry.
- Display source, acquisition age, confidence and stale state in the UI.
- Preserve an audit trail for every publish or dismiss action.

### 3.2 Out of scope

- Treating raw or unverified satellite observations as verified hazards.
- Automatic rerouting from an unverified flood polygon.
- Inferring flood depth or vehicle clearance from Sentinel-1 alone.
- Redistributing raw Sentinel-1 scenes to the mobile app or public portal.
- A public satellite-imagery portal.
- Interferometric, subsidence or change-detection products beyond the approved
  flood-extent workflow.
- Public App Store or Play Store release and other unresolved distribution
  decisions.
- Replacing citizen reports, sensors or dispatcher authoring; this is an
  additional source.

## 4. Proposed Architecture

| Area | Proposed change |
| ---- | --------------- |
| Satellite source | Sentinel-1 SAR, with the access route and processing service recorded in `OD-D24`. |
| Credential | Provider-issued credential stored in the backend secret store. No credential is embedded in the mobile app, admin bundle, repository or logs. The access provider's OAuth/client-credential flow `[TBC]` is preferred over a static shared key. |
| Acquisition | Scheduled worker searches for approved Sentinel-1 products over the coverage area and records product metadata before processing. |
| Processing | Derive water/flood extent from Sentinel-1 GRD data using an approved threshold/change-detection workflow with terrain, urban, vegetation and radar-artefact masks; or consume an approved derived-flood product. Exact algorithm and product level are `[TBC]`. |
| Observation | Store flood polygons, confidence, source product ID, acquisition time, processing time, coverage and review status as a flood observation, not a hazard. |
| Correlation | Intersect the observation with road edges and nearby sensors/reports; surface the evidence and uncertainty to the reviewer. |
| Verification | Dispatcher reviews and either publishes a hazard polygon/closure, merges it with an existing hazard, or dismisses it with a reason. Confidence-threshold auto-publish is not enabled until explicitly approved. |
| Eventing | Verified hazards use the existing hazard stream; pending observations are visible only to authorised admin users. |
| Offline Areas | The package contains the latest verified satellite flood polygons plus acquisition time, confidence, source and expiry. Raw scenes and credentials are never bundled. |
| Storage | Admin/backend stores observation metadata and derived geometry. Raw Sentinel-1 scenes remain in provider storage or an approved processing environment, not on mobile. |
| Security | Service-to-service authentication, least-privilege credentials, token caching, rotation, quota monitoring and redacted logs. |
| Licensing | Copernicus Sentinel data attribution and derived-layer/offline use must be confirmed before release. Sentinel data is generally free and open, but processing services and derived-layer redistribution may carry terms and costs `[TBC]`. |

## 5. Proposed API Surface

| Method | Path | Purpose |
| ------ | ---- | ------- |
| `POST` | `/api/v1/flood-observations` | Service-to-service ingest of a processed Sentinel-1 observation. |
| `GET` | `/api/v1/flood-observations` | List observations with source, acquisition time, confidence and status for authorised reviewers. |
| `GET` | `/api/v1/flood-observations/{observation_id}` | Return geometry, source product and evidence for review. |
| `POST` | `/api/v1/flood-observations/{observation_id}/publish` | Publish a verified hazard from the observation. |
| `POST` | `/api/v1/flood-observations/{observation_id}/dismiss` | Dismiss with a reason and retain the audit record. |

The existing `/api/v1/hazards` and hazard stream remain the client-facing path
for verified hazards. Raw Sentinel-1 ingestion is internal and must not be
reachable with a mobile or public credential. Final shapes belong in
`docs/api.md` after approval.

## 7. Risks and Controls

| Risk | Control |
| ---- | ------- |
| Satellite extent is mistaken for water depth or safe passability | Keep observations advisory; require depth/passability evidence or reviewer confirmation before routing. |
| Revisit gap or processing delay makes the observation stale | Show acquisition time and expiry; keep the last verified snapshot but label it stale; do not claim live coverage. |
| Radar artefacts, wind, vegetation or urban shadow create false water | Use approved masks, confidence scoring and reviewer validation; retain the source product for audit. |
| Credential leakage or quota exhaustion | Backend-only secret, rotation, least privilege, quota alerts, fail-closed ingest. |
| Raw imagery redistribution breaches terms | Store derived polygons only; confirm Copernicus attribution and offline rights before release. |
| A satellite hazard conflicts with a field report | Reviewer sees both; merge, replace or dismiss with an audited reason. |
| Provider outage blocks updates | Continue with last known verified snapshot and existing reports/sensors; show degraded state. |
